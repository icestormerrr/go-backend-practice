## Что реализовано

- один общий сервисный слой `internal/task.Service`
- один и тот же набор тестовых данных для REST и GraphQL
- REST API:
  - `GET /v1/tasks`
  - `GET /v1/tasks/{id}`
  - `POST /v1/tasks`
  - `PATCH /v1/tasks/{id}`
- GraphQL API:
  - `POST /query`
  - Playground на `/`
- unit-тест для общего сервисного слоя

Обе API работают поверх одной модели:

```go
type Task struct {
    ID          string `json:"id"`
    Title       string `json:"title"`
    Description string `json:"description"`
    Done        bool   `json:"done"`
}
```

## Единый сценарий сравнения

Для сравнения зафиксирован один и тот же пользовательский сценарий:

1. экран списка задач использует поля `id`, `title`, `done`
2. экран деталей использует поля `id`, `title`, `description`, `done`
3. дополнительное действие: создание новой задачи и обновление поля `done`

Это позволяет сравнивать не разные проекты, а один и тот же клиентский сценарий.

## Сравнение количества запросов

Для сценария `список задач -> открыть детали -> обновить done` количество сетевых обращений одинаковое.

REST:

1. `GET /v1/tasks`
2. `GET /v1/tasks/{id}`
3. `PATCH /v1/tasks/{id}`

GraphQL:

1. `query { tasks { id title done } }`
2. `query GetTask($id: ID!) { task(id: $id) { id title description done } }`
3. `mutation Update(...)`

Вывод: в простом CRUD-сценарии GraphQL не уменьшает число запросов автоматически. Его преимущество проявляется в точности структуры данных.

## Сравнение скорости

Для дополнительного сравнения выполнен отдельный сценарий:

- REST: много раз подряд вызывается `GET /v1/tasks`, который возвращает список задач со всеми полями
- GraphQL: много раз подряд вызывается `POST /query`, который запрашивает только `id`

Идея такого теста: посмотреть, как влияет over-fetching на время серии одинаковых запросов. Один запрос на localhost обычно слишком быстрый, поэтому замер делается в цикле.

### Скрипт замера

Файл:

`scripts/compare_speed.ps1`

Запуск:

```powershell
.\scripts\compare_speed.ps1 -Iterations 1000
```

Основная идея скрипта:

```powershell
$restMeasure = Measure-Command {
  for ($i = 0; $i -lt $Iterations; $i++) {
    $null = Invoke-WebRequest -UseBasicParsing http://localhost:8080/v1/tasks
  }
}

$graphqlBody = @{
  query = "query { tasks { id } }"
} | ConvertTo-Json -Compress

$graphqlMeasure = Measure-Command {
  for ($i = 0; $i -lt $Iterations; $i++) {
    $null = Invoke-WebRequest `
      -UseBasicParsing `
      -Uri http://localhost:8080/query `
      -Method Post `
      -ContentType "application/json" `
      -Body $graphqlBody
  }
}
```

### Практический результат

Замер выполнен локально на одном и том же сервере при `1000` итерациях.

![alt text](docs/docs/image-3.png)

Практический вывод по этому тесту: при запросе только списка идентификаторов GraphQL в данном проекте оказался быстрее, потому что передаёт меньший объём данных. Но важно отметить, что разница очень небольшая, тк различие в объёме передаваемых данных очень небольшое. Следовательно gql надстройка имеет смысл только в действительно сложных сценариях.

## Сравнение объёма данных

Сравнение выполнено на реальных ответах локально запущенного сервера.

### Экран списка

Клиенту нужны только поля `id`, `title`, `done`.

- REST-ответ списка: `300` байт
![alt text](docs/docs/image.png)
- GraphQL-ответ списка: `195` байт
![alt text](docs/docs/image-4.png)
Причина различия:

- REST возвращает ещё и `description`, хотя экран списка это поле не использует
- GraphQL позволяет явно запросить только нужные поля

Это пример `over-fetching` в REST.

### Экран деталей

Клиенту нужны поля `id`, `title`, `description`, `done`.

- REST-ответ детали: `157` байт
- GraphQL-ответ детали: `174` байта

Здесь GraphQL уже не выигрывает по размеру, потому что нужен полный набор полей, а поверх ответа добавляется обёртка `data`.

Вывод: GraphQL особенно полезен там, где у разных экранов разные наборы полей. Если нужен весь объект целиком, выигрыш может отсутствовать.

### GraphQL

Запрос:

```graphql
    id
    title
    description
    done
  }
}
```

Переменные:

```json
{
  "id": "unknown"
}
```

Ответ:

![alt text](docs/docs/image-2.png)

При этом HTTP-статус остаётся `200 OK`.

Вывод по ошибкам:

- в REST ошибка проще читается начинающим разработчиком, потому что сразу видно `404`
- в GraphQL клиент должен дополнительно анализировать поле `errors`
- для журналирования и мониторинга REST обычно проще, так как он естественно опирается на HTTP-статусы

## Документирование и тестирование

REST в учебном контексте оказался проще для первого знакомства:

- есть отдельные URL и понятные HTTP-методы
- запросы удобно повторять через `curl` и `Invoke-WebRequest`
- REST хорошо сочетается с Swagger/OpenAPI

GraphQL в учебном контексте оказался гибче, но чуть сложнее:

- используется один endpoint
- клиенту нужно понимать схему, `query`, `mutation`, типы и переменные
- при этом Playground делает API самодокументируемым и удобным для экспериментов

Если цель занятия — быстро показать CRUD и HTTP-методы, REST проще. Если цель — показать гибкий выбор полей и разную форму ответов под разные экраны, GraphQL нагляднее.

## Кэширование

Сравнение выполнено концептуально.

- в REST кэширование проще организовать по URL и HTTP-методам
- в GraphQL единый endpoint усложняет использование стандартного HTTP-кэша
- для GraphQL чаще нужны дополнительные подходы: client-side cache, persisted queries, кэширование на уровне данных

Поэтому для простых CRUD API REST обычно удобнее и дешевле в сопровождении.

## Итоговая таблица

| Критерий | REST | GraphQL |

| Структура API | Несколько endpoint | Один endpoint |

## Итоговый вывод

На выбранном сценарии REST и GraphQL решают одну и ту же задачу, но делают это по-разному. В простом CRUD-сервисе количество запросов у них может быть одинаковым, поэтому GraphQL не стоит считать автоматическим способом уменьшить сетевые обращения. Основное практическое преимущество GraphQL в этой работе проявилось на экране списка задач, где клиенту нужны не все поля объекта. В REST сервер вернул лишнее поле `description`, а GraphQL позволил получить только действительно нужные данные. При этом для экрана деталей, где клиенту нужен полный объект, выигрыш GraphQL по объёму ответа уже исчез. REST оказался проще по маршрутам, по обработке ошибок и по логике кэширования. GraphQL оказался гибче для клиента, но потребовал отдельной схемы, генерации кода и более внимательной обработки ошибок через поле `errors`. 

Поэтому для внутренних CRUD-сервисов и учебных административных API REST чаще является более рациональным решением. GraphQL имеет смысл выбирать там, где есть несколько разных клиентов, сложные интерфейсы и потребность точно управлять набором возвращаемых полей. 
Важно понимать, что объём данных между backend сервисом и сервисом базы данных (если бы она была) останется одинаковым в обоих случаях, а следовательно, если сервис требует настоящего high load, то оптимизации только на стыке backend / frontend будет не достаточно.
